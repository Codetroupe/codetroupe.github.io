YOUR FIRST COMPONENT

Choose. Inspect.
Make it part of your app.

Start with a Google API integration, generate a separate Kotlin or Java component, then connect its initialization and callbacks to your existing Android app.

About 6 stepsKotlin + JavaDevelopment build 0.1.8
01 / REQUIREMENTS

Check your setup.

Use Android Studio or IntelliJ IDEA based on IntelliJ Platform build 261 or newer, and open your Android Gradle project. The current package has passed compatibility verification against IDEA and Android Studio 261; an open-ended build range does not mean every future IDE has already been tested.

Browsing the local templates does not require a Google account, OAuth token or service-account key. Configuring Google Play or Firebase for the Android app is a separate step.

Before the commercial release

The current 0.1.8 package is for development testing. Commercial activation is not implemented yet. The planned product is paid and closed source, with no trial; this public guide is available to read before purchase. See licensing and availability.

02 / OPEN

Find the puzzle button.

If you have a developer-provided package, choose Settings → Plugins → gear menu → Install Plugin from Disk…, select the ZIP and restart if prompted. This local installation is a development workflow, not the final purchase or activation process.

Open Tools → GooglePlay API, or select the puzzle button in the tool-window bar. On a fresh New UI layout it appears in the lower-left group and opens a bottom-docked panel. Existing saved positions are respected; use the IDE’s Move to → Bottom action to reposition it.

ComponentsChecksChanges
03 / INSPECT

Read the code before generating.

Choose an integration from Components. The preview includes Code, Initialize and Setup. Switch between Kotlin and Java; for In-app updates, choose Flexible or Immediate in the Update mode control.

  • Code shows the reusable component.
  • Initialize shows calls and lifecycle hooks to merge into your app.
  • Setup describes dependencies, prerequisites and official sources.

The Official docs link opens the SDK documentation in your browser. Preview can be used outside Android projects; writing files requires a detected Android module.

04 / CONFIGURE

Give the component a home.

Choose Generate…, select the target module and language, then choose your component package and class name. A blank package uses the module namespace plus .googleplay, with the application ID as a fallback.

Optionally generate a separate Activity or Application example. The existing entry-class field customizes instructions; it does not insert code into that class or replace your launcher.

EXAMPLE / IN-APP REVIEW
app/
├─ src/main/kotlin/com/example/app/googleplay/
│  ├─ RatingComponent.kt
│  └─ examples/RatingComponentExampleActivity.kt  (optional)
├─ docs/googleplay-api/play.in-app-review/README.md
└─ build.gradle.kts  (when direct dependency merging is supported)

Java output uses the Java source directory. Groovy builds, aliases and version catalogs receive dependency merge guidance rather than a complete automated migration.

05 / REVIEW

Review each planned file.

Save relevant editor files and commit or back up your project. Under Changes, inspect the proposed source, existing content and Gradle changes before choosing Apply Changes. Different existing files trigger a conflict; selecting another update mode does not migrate a customized component.

Current development-build file handling

Apply checks files on disk and does not reconcile unsaved editor content or provide native IDE Undo. Snapshot rollback can restore or delete affected files without preserving later edits. Do not use Rollback Last Apply after editing those files; use version control or reviewed manual recovery. These behaviors need hardening before public release.

After Apply, the generated component opens in the editor. Read its integration guide alongside the resulting project diff.

06 / CONNECT

Finish the integration in your app.

  1. Merge initialization, callbacks and cleanup into your existing Activity or Application.
  2. Keep current Manifest registrations and custom superclasses. Register a new example component only if you choose to use it.
  3. Merge dependency/plugin declarations using your project’s existing version owner, then sync Gradle.
  4. Complete service configuration and backend work, then test the runtime flow.

The generated components can be called from Views or Compose event handlers. They do not generate a complete app screen or automatically connect to your ViewModel or dependency-injection setup.

In-app updatesOffer a background download or a full-screen update flow, with the lifecycle code in a reusable component.↗In-app reviewRequest the Google Play review flow after a meaningful moment in your app, without tying it to your app architecture.↗App integrityGenerate the client side of a Play Integrity Classic request, with a clear boundary for backend verification.↗SubscriptionsKeep Billing client setup, product queries and purchase callbacks in one reusable Android component.↗FirebaseSet up Analytics and Crashlytics with initialization, event and error methods, and explicit collection controls.↗

The Checks tab performs basic local project checks. It does not validate Play Console setup, backend security, Firebase report delivery or full release compliance.

A few things worth checking.

No Android module is available.

Open the Android project root and verify that its Android Gradle configuration can be detected. You can still inspect the templates without selecting a module.

Generated imports are unresolved.

Merge the generated dependency guidance and sync Gradle. Check repository declarations and keep a single version owner instead of adding literal versions alongside a catalog or root declaration.

The component already exists.

Compare the existing class with the proposed file. Preserve your customization or generate with another package/class name. Switching a mode is not an overwrite or migration command.

The review or update flow does not appear.

Google Play controls availability, eligibility and quotas. Follow each integration’s official test setup rather than treating a local debug APK as proof of the Play runtime experience.
